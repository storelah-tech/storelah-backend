### 1.4 `saveVersion` vs per-Update snapshots on `(modelId, version)`

- `FinancialModelVersion @@unique([modelId, version)]` (`schema.prisma:2099`–`:2111`); `saveVersion` (`library.ts:125`–`:157`), submit (`:205`–`:240`), approve/reject (`:242`–`:303`), publish (`:431`–`:479`) all compute `next = max(version)+1` (or `latestVersionRow` pre-read) and then `create` inside `$transaction` — with NO row lock on the parent. Two concurrent writers can compute the same `next` → the loser gets `P2002` (surfaces as 500 today, not 409). Same TOCTOU shape in `updateModelSection`: `assertFreshVersion` runs pre-transaction (`models.ts:274`), so two concurrent Updates both pass CAS and both write `version+1` — last-writer-wins, silent on the model row (history snapshots themselves never collide because nothing else writes them).
- For the new `FinancialModelCalculation` with `@@unique([modelId, modelVersion])` + `@@unique([modelId, idempotencyKey])` this is SAFE provided P5 does all three: (a) idempotency-Key replay returns the existing calculation row without re-projecting; (b) the after-commit valuation write is conditional on `modelVersion` (stale result discarded, never overwrites a newer calculation — brief §5 "stale discarded"); (c) the model-row bump moves to a conditional update (`where: {id, version: expected}` → `P2025` mapped to 409 STALE) instead of the current pre-check, at least on the lease route. (c) also fixes the existing lost-update window for this route without changing other routes' behaviour.
- `saveVersion` itself needs NO change: per-Update snapshots go to the new Calculation table, not to `FinancialModelVersion`; version-history numbering is untouched (D5 read-only view reads the existing table).
